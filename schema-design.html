Database schema design

PostgreSQL schema for the LLM-curated 16S database. Draft v0.1 was designed before any study had been curated. v0.2 is revised against five real IBD studies (573 16S runs) curated by agents in studies/: every hard case they hit is shown below with the table that stores it.

Every table and field is still a proposal. Click Comment on any field (or Comment on table / Propose a field) to mark it as looks right, change, remove, or question. Feedback is kept in this browser. When you are done, open Feedback, copy the Markdown, and paste it into the chat.

What changed from v0.1, and why

  • The database stores facts; analysis decisions live in views. v0.1 put disease_status (case/control) and include_in_analysis on core.sample. Real studies showed these are judgement calls that depend on the question: are healthy siblings of patients controls (PMID 28174747)? Is "UC with C. difficile infection" a plain UC case (35756051)? Those now live in analysis.cohort_definition, so a data scientist can define a strict or a broad cohort over the same facts.
  • One long observation table for every subject-, sample- and run-level value. core.sample_label becomes core.observation. It holds several values for the same field from different sources, so a conflict is stored instead of erased. In 23013615 the authors' sex codes are the inverse of the paper's Table 1 in every group: both readings are kept, neither is accepted, and a task records why.
  • A field dictionary and per-study value maps tame the heterogeneity. The five studies used host_sex, sex and gender; Normal, HC, Control and DZ for controls. core.field_dictionary names each concept once and lists its synonyms; core.value_map records, per study, how each raw value was mapped and on what evidence. Fields not in the dictionary still go in, flagged as unregistered, and are promoted to columns once enough studies use them.
  • The paper's own groups and every number it states become rows. Studies had 3 to 9 groups (HC/UCN/UCP, probands/siblings/parents, Inf_M/Uinf_M) and stated anywhere from 17 to 99 checkable numbers. core.study_group and core.reported_count replace the fixed n_case_reported-style columns, and every validation check points to the number it tested.
  • Raw archive text beyond BioSample attributes. Labels sat in the BioSample sample name (35756051) and in the SRA experiment title (37661264). raw.biosample_attribute becomes raw.archive_attribute, covering BioSample, SRA experiment, run and ENA sample fields.
  • Every run is stored, including ones the paper did not use. Archives held WGS runs next to 16S (29335008, 23013615), runs the authors excluded, pilot runs, and a pooled "unmatched barcodes" run. core.run gains assay and used_in_paper; core.sample.sample_role gains technical_pool.
  • Subjects can be unknown, inferred, or related. 37661264 never says which biopsies come from the same patient; 23013615 counts samples as patients; 28174747 recruits whole families. core.subject gains family_key (relatives must stay on one side of a train/test split) and core.sample gains subject_link.
  • Where a document came from matters. The per-sample labels for 23013615 exist only in a third-party copy on Zenodo of a file from a dead lab server. core.document.origin records that, so a cohort can include or exclude such sources.

Design principles

  • Store everything, decide later. Every API response, parsed supplementary table, and LLM response is kept verbatim in the raw layer. Curated values can be re-derived from it when rules change, without re-downloading or re-calling a model.
  • Facts, not decisions. Curated tables record what a source says (diagnosis, relationship, infection status, whether the authors used the sample). Who counts as a case or a control, and which samples enter a model, is decided in analysis.cohort_definition, so the same facts serve a strict and a broad cohort.
  • Every curated value has a source, and conflicts are kept. Study-level facts point to an extraction row with a verbatim evidence quote; subject-, sample- and run-level values are rows in core.observation that say where the value was found (archive attribute, spreadsheet cell, PDF table, external file, or a person). Two sources that disagree become two rows, not one guess.
  • Typed columns for common fields, a dictionary for the long tail. A handful of fields every study has (diagnosis, sex, age, sample type, body site) are typed columns. Everything else is an observation whose field name is registered in core.field_dictionary, or flagged as unregistered until enough studies use it to promote it.
  • Technical covariates on every run. Region, primers, platform, instrument, layout, read length, extraction kit, pipeline version, and reference database are reachable from each run, so the later batch-effect analysis needs no new columns.
  • Sequences, not just taxonomy. ASV sequences and raw counts are stored, so ASVs can be re-classified against a new reference without re-running DADA2.
  • "Control" is never ambiguous. A healthy control subject (diagnosis = healthy) and a negative-control or blank sample (sample_role = negative_control) are different columns.
  • One append-only activity log for agents, scripts, and people.

Layers

How the main tables connect

Conventions used in every table

  • Postgres schemas = layers. raw, core (curated), bio (bioinformatics output), ops (log, tasks, checks), analysis (views only).
  • Keys. Internal ids are bigint generated always as identity. Public accessions (PMID, BioProject, BioSample, run) are stored as text with a unique constraint; run and project accessions are used directly as primary keys because they are stable and globally unique.
  • Controlled values are text columns with a CHECK constraint (not Postgres ENUM types), so adding a value is a one-line migration. Allowed values are listed in each field's description.
  • Time. All timestamps are timestamptz in UTC. Every core and bio table also has created_at and updated_at (not repeated below).
  • Not null. NN marks required fields; everything else may be null, meaning "not known yet". Unknown is never stored as an invented default.
  • Personal data. Only what the paper or archive already published (sex, age, BMI, country). No names or direct identifiers.
  • Files (PDFs, supplements, FASTQ) live on disk under DATA_DIR outside git; the database stores their path and SHA-256. FASTQ is temporary: it is deleted once the study's ASV and count tables are loaded (see run.download_state), because the full IBD set would need 1.2–2 TB.
